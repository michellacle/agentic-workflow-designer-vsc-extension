Problem.

The designer module calls acquireVsCodeApi() on load and scatters vscode.postMessage across ~18 call sites. There's no seam — the interface is the VS Code API. Running it outside VS Code requires faking the entire API surface, and the current tests use new Function() to eval the built JS which is fragile and slow.

Solution.

Extract a MessagingHarness interface (3 methods: post(), getState(), setState()) and inject it via a module-level setter or IIFE parameter. Provide two adapters: VSCodeHarness (production, delegates to acquireVsCodeApi()) and TestingHarness (captures messages in memory, supports event-driven assertions). The designer becomes a deep module — canvas rendering, state machine, and event handling behind a 3-method interface.

Wins.

  • Locality: All VS Code coupling concentrates in one thin adapter
  • Leverage: One interface enables browser dev, standalone HTML, and jest tests
  • Depth: Designer's interface shrinks from ~18 vscode calls to 3 harness methods
  • Hot reload: Standalone HTML + Vite dev server, no extension build cycle
  • Tests: TestingHarness captures messages for assertion, no more new Function()

2. Standalone HTML runner with Vite hot reload

Strong
webview/test.html · webview/src/designer.ts · scripts/standalone-dev.js (new)

Before — Build → Install → Reload cycle

1. npm run compile (TS → JS)
2. npm run build-webview (bundle)
3. F5 launch extension host
4. Open .workflow.yaml file
5. Manual test in webview

After — Browser + HMR

1. npm run dev:standalone
2. Browser opens with designer
3. Edit → instant HMR refresh

Problem.

Testing a canvas rendering change requires compiling TypeScript, bundling the webview, launching an extension host, opening a workflow file, and hoping the webview loads. This is 5 steps with ~30 seconds of wait time. The feedback loop kills momentum.

Solution.

A Vite dev server that serves webview/test.html with the TestingHarness injected. The designer loads as a native ES module (no IIFE bundling), so Vite's HMR works out of the box. A npm run dev:standalone script starts the server and opens the browser.

Wins.

  • Locality: Design changes verified in-browser, no extension reload
  • Leverage: Same code path as production, just different harness adapter
  • Feedback loop: Sub-second HMR vs. 30-second extension reload

3. Convert the designer IIFE to an ES module

Worth exploring
webview/src/designer.ts · webview/src/tsconfig.json

Before — IIFE, global state, no exports

(function () {
  'use strict';
  const state = { ... };       // global
  let vscode = acquireVsCodeApi();
  function showError(msg) { }  // global
  function draw() { }          // global
  // ... 3000+ lines
})();

After — ES module, explicit init

export function createDesigner(
  harness: MessagingHarness,
  container: HTMLElement
): DesignerApi {
  const state = { ... };
  function draw() { }
  return {
    init(workflow, options),
    send(message),
    destroy()
  };
}

Problem.

The designer is a 3000+ line IIFE with global mutable state. It can't be imported, tested in isolation, or HMR'd properly. The current test approach (new Function(builtJs)) is a workaround for the lack of a module interface.

Solution.

Convert to an ES module that exports createDesigner(harness, container). The factory accepts a MessagingHarness and a DOM container, returns a small DesignerApi with init(), send(), and destroy(). The IIFE wrapper becomes a thin bootstrap that calls createDesigner(new VSCodeHarness(), document.body).

Wins.

  • Depth: Factory function is the interface; 3000 lines of implementation behind it
  • Locality: State is scoped to the factory closure, not global
  • Test surface: Tests call createDesigner(testingHarness, container) directly
  • HMR: Vite can hot-reload ES modules natively

4. Runtime seams are already deep (context, not a candidate)

Already Good
src/runtime/executionObserver.interface.ts · src/runtime/executionContext.ts · src/runtime/workflowExecutor.ts

The Runtime already follows the deep module pattern well. WorkflowExecutor has a small interface (run(), pause(), stop(), onDidChangeState) and sits behind two seams: ExecutionObserver (VSCode vs. InMemory adapters) and IAgentInvoker (real vs. mock). The deletion test passes — removing WorkflowExecutor would scatter execution logic across all callers. This is already deep. No action needed here.

Top Recommendation

Tackle Candidate 1 + 2 together — they're mutually reinforcing. The TestingHarness adapter (Candidate 1) is the seam; the standalone HTML runner (Candidate 2) is the first non-production adapter that benefits from it.

Converting the IIFE to an ES module (Candidate 3) is the natural next step once the harness seam exists — it concentrates all the "how do we load this?" complexity into one factory function.

Estimated effort: 1-2 days for the harness + standalone runner. Immediate payoff: sub-second feedback loop for canvas/designer changes, no more extension build-install-reload cycles.
